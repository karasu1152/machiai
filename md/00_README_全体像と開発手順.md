## 1. 何を作るのか（30秒で）

ホテルに3種類の画面を置く。

```
┌──────────────┐   ①発券         ┌──────────────┐
│  発券キオスク  │ ──────────────▶ │              │
│   (iPad)     │                 │              │
└──────────────┘                 │              │
       │                         │   Supabase   │
       │ ②印刷ジョブ投入          │  (無料枠)     │
       ▼                         │              │
┌──────────────┐  ③ポーリング取得  │   DB +       │
│ サーマルプリンタ│ ◀────────────── │   Realtime   │
│  (ロール紙)   │                  │              │
└──────────────┘                 │              │
       │ ④券が出る                └──────────────┘
       ▼                            ▲    ▲    ▲
   [ C-012 ]                        │    │    │
   [  QR   ] ─────⑤QRを読む──────────┘    │    │
                                          │    │
┌──────────────┐  ⑥呼び出し操作           │    │
│ スタッフ画面   │ ───────────────────────┘    │
│   (iPad)     │                              │
└──────────────┘                              │
                                              │
┌──────────────┐  ⑦呼出番号を表示＋音声       │
│  サイネージ    │ ◀───────────────────────────┘
│ (iPad / TV)  │
└──────────────┘
```

1. ゲストがiPadで「チェックイン」または「レストラン」を選ぶ
2. 番号札がロール紙で即座に印刷される（QRコード付き）
3. QRを読むとスマホで自分の順番がリアルタイムに見える
4. スタッフがiPadで「次を呼ぶ」を押す
5. サイネージに番号が大きく出て、音声で呼び上げる。ゲストのスマホも同時に赤く光る

| 領域 | 採用 | 月額 | 選定理由 |

| 印刷 | **Star mC-Print3 (CloudPRNT)** | ¥0 | プリンタ側からサーバーを**ポーリング**する方式。iPad側に一切の追加アプリ・設定が不要 |

| ドメイン | `xxx.pages.dev` または独自ドメイン | ¥0〜1,500/年 | 独自ドメインは任意 |

### ⚠️ Vercel を採用しなかった理由（重要）

Vercel の Hobby（無料）プランは利用規約で**商用利用が明確に禁止**されています。

> "Hobby teams are restricted to non-commercial personal use only. All commercial usage of the platform requires either a Pro or Enterprise plan."
> — Vercel Fair Use Guidelines

ホテルの業務システムは疑いなく商用利用に該当するため、Vercel を使うなら Pro プラン（$20/月〜）が必須になります。
**Cloudflare Pages の無料プランには商用利用の制限がありません**。「限りなくコストを低く」という要件を満たすには Cloudflare 一択です。

## 3. Supabase 無料枠で足りるかの試算

ホテル1館・1日300組の発券を想定した場合。

| 項目 | 無料枠 | 想定使用量 | 判定 |
|---|---|---|---|
| DBサイズ | 500 MB | 1チケット約400B × 300組 × 365日 = 約44MB/年 | ✅ 十分（10年運用可） |
| Realtime 同時接続 | 200 | キオスク1 + スタッフ3 + サイネージ1 + ゲスト最大40 = 45 | ✅ 十分 |
| 月間アクティブユーザー | 50,000 | スタッフ数名のみ（ゲストは匿名RPC） | ✅ 十分 |
| Edge Functions 呼び出し | 500,000/月 | プリンタのポーリング(5秒間隔×15h/日) = 約324,000/月 | ⚠️ **要調整** |
| 帯域 | 5 GB/月 | SPA本体はCloudflare配信のため、API通信のみで数百MB | ✅ 十分 |

**⚠️ プリンタのポーリング間隔は「営業時間中10秒 / 営業時間外は停止」に設定すること。**
5秒間隔で24時間動かすと Edge Function の無料枠を超えます。詳細は `07_印刷仕様書.md` の「ポーリング間隔の最適化」参照。

### 無料枠の落とし穴と対策

| 落とし穴 | 対策 |
|---|---|
| **7日間DBアクセスがないとプロジェクトが自動停止** | ホテルは毎日稼働するため実質発生しない。長期休業する場合は GitHub Actions で日次 `SELECT 1` を打つ |
| **無料プランは自動バックアップなし** | GitHub Actions で日次 `pg_dump` → リポジトリにコミット（`03_システム設計書.md` にワークフロー記載） |
| **Realtime 200接続は「同時」の上限** | ゲストのステータス画面は5分無操作で自動切断する実装を入れる |

## 4. iOS の通知制約について（正直な話）

**iPhone / iPad の Safari は、Webサイトから通知を送るのに「ホーム画面に追加」が必須です。** これは2026年8月現在も変わっていません。

ホテルのゲストに「ホーム画面に追加してください」とお願いするのは現実的ではないため、本システムでは**通知に頼らない設計**を採用します。

| 手段 | iOS | Android | 本システムでの位置づけ |
|---|---|---|---|
| ステータス画面のリアルタイム更新 | ✅ | ✅ | **主たる手段。** 画面を開いている間、順位が自動で減っていく |
| 呼び出し時の画面全面フラッシュ＋音 | ✅ | ✅ | **主たる手段。** 画面を開いたまま待ってもらう（Screen Wake Lock で消灯も防ぐ） |
| Web Push 通知 | △ ホーム画面追加時のみ | ✅ | **補助。** 対応端末では「あと2組」で自動通知 |
| 館内サイネージ + 音声呼び上げ | ✅ | ✅ | **主たる手段。** スマホを見ていない人向けの保険 |
| SMS / LINE | — | — | **不採用。** 従量課金・公式アカウント契約が必要で「無料」要件に反する |

券面には多言語で「**この画面を開いたままお待ちください**」と印字し、ステータス画面には「画面を閉じても、館内モニターでお呼び出しします」と表示することで運用をカバーします。

## 5. 開発の進め方（推奨6フェーズ）

各フェーズの終わりに動作するものができる構成にしています。

| Phase | 内容 | 目安 | 完了条件 |
|---|---|---|---|
| **0. 環境構築** | Supabaseプロジェクト作成、DDL適用、Cloudflare Pages接続 | 0.5日 | DBにテーブルが存在し、空のSPAが公開URLで開く |
| **1. コア発券** | 発券キオスク画面 + `issue_ticket` RPC + スタッフ画面の一覧表示 | 2日 | iPadで発券ボタンを押すと、スタッフ画面に番号が現れる |
| **2. 呼び出し** | 呼出/完了/不在の操作、Realtime同期、サイネージ画面 | 2日 | 「次を呼ぶ」でサイネージに番号が出て音声が鳴る |
| **3. 印刷** | Edge Function `cloudprnt` + プリンタ設定 + 券面デザイン | 2日 | 発券ボタンを押すとロール紙が出てくる |
| **4. ゲスト画面** | QRトークン、ステータス画面、リアルタイム順位表示、呼出フラッシュ | 1.5日 | 券のQRを読むと自分の順位が見え、呼ばれると赤く光る |
| **5. 管理・多言語・統計** | キュー設定画面、4言語対応、統計ダッシュボード、Web Push | 3日 | 管理者がキューを追加でき、日英中韓が切り替わる |
| **合計** | | **約11日** | |

### Phase 0 の具体的な手順

```bash
# 1. Supabase プロジェクト作成（無料プラン / リージョン: Northeast Asia (Tokyo)）
#    → https://supabase.com/dashboard

# 2. DDLを適用
#    SQL Editor に 04_データベース設計書.md の DDL を全文貼り付けて実行

# 3. フロントエンド雛形
npm create vite@latest machiai -- --template react-ts
cd machiai
npm i @supabase/supabase-js react-router-dom qrcode.react zustand
npm i -D tailwindcss @tailwindcss/vite

# 4. .env.local
#    VITE_SUPABASE_URL=https://xxxx.supabase.co
#    VITE_SUPABASE_ANON_KEY=eyJ...

# 5. Cloudflare Pages に接続
#    GitHubリポジトリをpush → Cloudflare Dashboard → Pages → Connect to Git
#    Build command: npm run build   /   Output directory: dist
#    環境変数に VITE_SUPABASE_URL と VITE_SUPABASE_ANON_KEY を設定

# 6. Edge Function（Phase 3で使用）
npx supabase functions deploy cloudprnt --no-verify-jwt   # ← --no-verify-jwt は必須
```

> **`--no-verify-jwt` を忘れないこと。** プリンタは Authorization ヘッダを送れないため、
> JWT検証が有効だとポーリングが全て401で弾かれ、印刷が一切動きません。

## 6. 段階導入のすすめ

いきなり全館導入せず、以下の順で広げることを推奨します。

1. **朝食レストランのみ** で2週間運用（1日1〜2時間のピークだけ。失敗しても影響が小さい）
2. 待ち時間推定の精度と、スタッフの操作習熟を確認
3. **フロントチェックイン**へ拡大（15:00のピーク時のみ稼働でも効果大）
4. 統計データが2週間分溜まったら、人員配置の見直しに活用

## 7. 将来の拡張余地（無料枠のまま可能なもの）

- **事前受付**：ゲストが客室のタブレットや自分のスマホから、フロントに来る前に発券
- **予約連携**：PMS（宿泊管理システム）のCSVを読み込み、部屋番号から予約者名を券面に印字
- **複数館対応**：`tenants` テーブルで既に対応済み。DDL変更なしでグループホテル展開可能
- **多言語の追加**：DBのカラム構造が言語ごとのJSONBなので、言語追加はデータ投入のみ

## 8. 設計の検証状況

`04_データベース設計書.md` のSQLは、**PostgreSQL 16 上で実際に実行して動作を確認済み**です。
（Supabase固有の `auth.uid()` / `anon` ロール / `supabase_realtime` パブリケーションはローカルで模擬）

| 確認項目 | 結果 |
|---|---|
| 全DDL・全関数がエラーなく適用される | ✅ 更地から一括実行して0エラー |
| 発券 → 採番 → `queue_states` 自動更新 | ✅ `R-001`〜`R-003` が連番で発行され、待機組数が同期 |
| 同一nonceの再送で二重発券しない | ✅ `duplicated: true` で同じ番号を返す |
| 2セッションが同時に `call_next` | ✅ `C-001` と `C-002`、**異なる番号**が返る |
| 不在 → 列の先頭に戻す | ✅ `sort_key` が最小値に更新され先頭に来る |
| エラー系（受付停止・上限到達・不正トークン） | ✅ `QUEUE_CLOSED` / `QUEUE_FULL` / `NOT_FOUND` |
| 券面マークアップの生成（日英） | ✅ QRコマンド・カット命令まで正しく出力 |
| 日次メンテナンス・時間帯別集計 | ✅ 時間帯ごとの発券数が正しく集計される |
| 待機202件での性能 | ✅ 発券 7.4ms / ステータス取得 5.3ms / 待機列取得 0.24ms |

検証の過程で見つけて修正した不具合を記録しておきます（設計書は修正済みです）。

1. **券面の改行が `\n` の2文字として印字されるバグ** — SQLの単一引用符内では `\n` はエスケープされません。`chr(10)` での連結に修正しました。
2. **時間帯別統計が常に1件になるバグ** — `jsonb_object_agg` で同一時間帯のキーが重複し、件数が上書きされていました。2段階集計に修正しました。

> 注意：テスト時に `tickets` へ直接INSERTすると `queues.last_number` は進みません。
> 通常運用では必ず `issue_ticket` を経由するため問題になりませんが、ダミーデータ投入後に
> 発券テストを行う場合は `queues.last_number` を手動で合わせてください。

## 9. 有料化を検討すべきタイミング

以下に該当したら Supabase Pro（$25/月）への移行を検討してください。それまでは無料で問題ありません。

- 1日の発券数が **1,000組** を超えた（DB容量・Edge Function呼び出しが逼迫）
- 同時にステータス画面を開くゲストが **150人** を超えた（Realtime接続上限）
- 障害時に**特定時点への復旧（PITR）** が業務上必須になった
