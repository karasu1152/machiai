## 1. システム構成

### 1.1 全体構成図

```
                        ┌─────────────────────────────────────┐
                        │      Cloudflare Pages (無料)        │
                        │   React SPA (静的配信・CDN)          │

                            │ HTTPS                      │ HTTPS ポーリング
                            │                            │ (10秒間隔)
                    ┌───────┴────────┐          ┌────────▼─────────┐
                    │  ゲストスマホ    │          │ Star mC-Print3   │
                    │  ステータス画面  │          │  (有線LAN)       │
                    └────────────────┘          └──────────────────┘
```

### 1.2 なぜこの構成か

| 判断 | 理由 |
|---|---|
| SPA（サーバーサイドレンダリングなし） | 静的配信のみで済むためCloudflare Pagesの無料枠に完全に収まる。SEO不要の業務システムにSSRは不要 |
| バックエンドをRPCに集約 | 匿名クライアントにテーブル直接書き込みを許さず、`SECURITY DEFINER` 関数のみを公開することで、採番の一貫性とセキュリティを同時に確保する |
| Edge Functionは3つだけ | Edge Functionの呼び出し回数が無料枠のボトルネックのため、通常操作はすべてRPC（DB直結）で処理し、Edge Functionは外部連携（プリンタ・Push）に限定する |
| プリンタがサーバーをポーリング | HTTPSページからLAN内のHTTPプリンタへは Mixed Content で通信できない。逆方向にすることでこの制約を根本回避し、かつiPad側の設定が一切不要になる |

## 2. チケットの状態遷移

### 2.1 状態一覧

| 状態 | 値 | 意味 | ゲスト画面の表示 |
|---|---|---|---|
| 待機中 | `waiting` | 発券済み、呼び出し前 | 「あと N組」 |
| 呼出中 | `called` | 呼び出したが未到着 | 全面赤＋「お呼び出し中です」 |
| 案内中 | `serving` | 到着し対応中 | 「ご案内中です」 |
| 完了 | `done` | 対応完了 | 「ありがとうございました」 |
| 不在 | `no_show` | 呼び出したが現れず | 「お呼び出しいたしましたが…受付までお声がけください」 |
| 取消 | `canceled` | キャンセル | 「この整理券は無効です」 |

### 2.2 遷移図

```
                        ┌──────────────────────────────────┐
                        │                                  │
                        │        [列に戻す(先頭/末尾)]       │
                        │                                  │
     発券               ▼                                  │
  ────────▶  ┌──────────────┐   次を呼ぶ/個別呼出  ┌────────┴─────┐
             │   waiting    │ ──────────────────▶ │   no_show    │
             │   待機中      │                     │    不在       │
             └──────┬───────┘                     └──────▲───────┘
                    │                                    │
                    │ 次を呼ぶ / 個別呼出                  │ 不在にする
                    ▼                                    │
             ┌──────────────┐                            │
             │    called    │ ───────────────────────────┘
             │    呼出中     │
             │              │◀────┐
             └──────┬───────┘     │ 再呼出(called_countを+1、状態は変わらず)
                    │             └─────┘
                    │ 案内開始
                    ▼
             ┌──────────────┐
             │   serving    │
             │    案内中     │
             └──────┬───────┘
                    │ 完了
                    ▼
             ┌──────────────┐
             │     done     │  ← 終端
             │     完了      │
             └──────────────┘

   ※ waiting / called / serving のいずれからも canceled へ遷移可能（取消）
   ※ called から直接 done へ遷移可能（呼んですぐ完了する運用向けのショートカット）
```

### 2.3 遷移時に記録するフィールド

| 遷移 | 更新するカラム |
|---|---|
| 発券 | `issued_at = now()`, `status = 'waiting'` |
| 呼出 | `called_at = now()`（初回のみ）, `called_count += 1`, `counter_id`, `status = 'called'` |
| 再呼出 | `called_count += 1`, `last_called_at = now()`（`called_at` は変えない） |
| 案内開始 | `served_at = now()`, `status = 'serving'`, `wait_seconds = served_at - issued_at` |
| 完了 | `finished_at = now()`, `status = 'done'`, `service_seconds = finished_at - served_at` |
| 不在 | `status = 'no_show'`, `no_show_at = now()` |
| 列に戻す | `status = 'waiting'`, `requeued_at = now()`, `sort_key` を先頭/末尾に応じて再設定 |
| 取消 | `status = 'canceled'`, `canceled_at = now()`, `cancel_reason` |

### 2.4 並び順の設計（`sort_key`）

「不在から列の先頭に戻す」を実現するため、発券順（`number`）とは別に **`sort_key`（double precision）** を持つ。

- 発券時：`sort_key = extract(epoch from now())`
- 末尾に戻す：`sort_key = (現在の最大値) + 1`
- 先頭に戻す：`sort_key = (現在の最小値) - 1`
- 任意位置への挿入：前後2件の `sort_key` の中間値を使う（浮動小数のため再採番不要）

待機列の取得は常に `ORDER BY sort_key ASC`。

## 3. 待ち時間推定アルゴリズム

### 3.1 方針

「前の組数 × 1組あたりの所要時間 ÷ 同時に捌ける窓口数」を基本とし、実績が溜まるまでは設定値を使う。

### 3.2 計算式

```
■ 入力
  P  = 自分より前の待機組数（sort_key が自分より小さい waiting の件数）
  S  = 1組あたりの平均サービス時間（秒）
  C  = 現在の実効窓口数

■ S の決定
  直近3時間以内に完了した（status='done'）チケットが 8件以上ある場合:
      S = median(service_seconds + (called_at→served_at の間隔))  ※直近20件
  それ未満の場合:
      S = queues.default_service_seconds （管理画面で設定、既定180秒）

■ C の決定
  C = 直近30分間に呼び出し操作を行った counter_id の distinct 件数
  ただし C < 1 のときは C = 1
  ただし C > queues.max_counters のときは C = queues.max_counters

■ 推定待ち時間（秒）
  T = ceil(P / C) * S

■ 表示への変換
  T < 60         → 「まもなく」
  60 <= T < 3600 → 5分単位に切り上げて「約 N 分」
  T >= 3600      → 「60分以上」

■ 手動上書き
  queues.manual_wait_minutes が NULL でない場合、上記を無視してその値を表示する
```

### 3.3 実装上の注意

- 推定値は**チケット発券時に一度だけ計算して券面に印字**し、ゲスト画面では**アクセスのたびに再計算**する。券面の値と画面の値が食い違うのは正常な挙動として、券面に「※目安です」と印字する。
- 中央値を使う理由：長時間の特殊対応（団体客・トラブル対応）が平均値を大きく歪めるため。
- 推定値を実態より**やや長めに出す**ほうが顧客満足度が高い（「思ったより早かった」を作る）。実装では計算結果に係数 1.1 を掛ける。

## 4. リアルタイム同期の設計

### 4.1 課題

Supabase Realtime は RLS を尊重する。ゲスト（匿名）が `tickets` テーブルを SELECT できない設計にすると、Realtime のイベントもゲストには届かない。かといって `tickets` を匿名に開放すると、他人の部屋番号まで見えてしまう。

### 4.2 解決策：公開ビュー用テーブル `queue_states`

個人情報を一切含まない、キューごとの「今の状況」だけを持つテーブルを別に用意し、これを匿名に開放する。

```
queue_states
├── queue_id            （PK）
├── tenant_id
├── now_serving_number  現在呼出中の表示番号  "C-012"
├── now_serving_counter 呼出先の窓口名        "2番カウンター"
├── called_seq          呼出通番（点滅トリガー用、呼ぶたびに+1）
├── waiting_count       待機組数
├── last_issued_number  最後に発券した番号
├── estimated_wait_sec  現在の推定待ち秒数
└── updated_at
```

このテーブルは `tickets` へのトリガーで自動更新される。

### 4.3 各画面の購読対象

| 画面 | 購読するもの | 更新時の動作 |
|---|---|---|
| ゲストステータス | `queue_states`（自分のキューのみ） | 変化を検知したら `get_ticket_status(token)` RPCを叩き直して自分の順位を再取得 |
| サイネージ | `queue_states`（全キュー） | `called_seq` が増えたら点滅＋音声再生 |
| スタッフ画面 | `tickets`（自テナント、認証済み） | 行の追加・更新を直接反映 |
| 発券キオスク | `queues`（受付状態） | `is_open` の変化でボタンの有効/無効を切替 |

### 4.4 なぜゲスト画面は直接データを受け取らないのか

`queue_states` の変化を「再取得のきっかけ」としてのみ使い、実データはRPCで取りに行く。
これにより、Realtime のペイロードに個人情報が一切乗らないことを構造的に保証できる。RPCの呼び出し回数は増えるが、DB直結のRPCは Edge Function と違って無料枠の対象外のため、コスト影響はない。

### 4.5 接続数の節約

無料枠の同時接続上限は200。以下で消費を抑える。

- ゲスト画面は `visibilitychange` を監視し、バックグラウンドで5分経過したら `channel.unsubscribe()` する
- フォアグラウンド復帰時に再購読し、同時に最新状態を1回取得する
- 終端状態（done / no_show / canceled）になったら即座に購読解除する

## 5. 二重呼び出しの防止

複数のスタッフ端末が同時に「次を呼ぶ」を押した場合、同じチケットが2回呼ばれてはならない。

`call_next` RPC の内部で、以下の行ロックを使って排他する。

```sql
SELECT id INTO v_ticket_id
FROM tickets
WHERE queue_id = p_queue_id AND status = 'waiting'
ORDER BY sort_key ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;   -- ← ここが要点
```

`FOR UPDATE SKIP LOCKED` により、片方の端末がロックした行はもう片方には見えず、次の待機者が返る。結果として、2台が同時に押すと**それぞれ異なる番号を呼ぶ**という、業務上望ましい挙動になる。

## 6. 業務日と番号リセット

### 6.1 業務日の定義

統計の集計単位を「業務日」とする。既定は **04:00 〜 翌03:59**（深夜営業を1日として扱うため）。

```sql
-- 業務日を求める関数
business_date(ts, tz, cutoff_hour) = (ts AT TIME ZONE tz - cutoff_hour * interval '1 hour')::date
```

### 6.2 番号リセット

`issue_ticket` RPC の内部で、キューの `last_reset_business_date` が現在の業務日と異なる場合、`last_number` を0にリセットしてから採番する。cronは不要で、最初の発券がリセットを兼ねる。

番号が `max_number`（既定999）に達したら1に戻る。

## 7. 印刷フローの設計

詳細は `07_印刷仕様書.md` を参照。ここでは全体の流れのみ示す。

```
[発券キオスク]                [Supabase]                    [プリンタ]
      │                            │                            │
      │  issue_ticket RPC          │                            │
      ├───────────────────────────▶│                            │
      │                            │ 1. tickets に INSERT       │
      │                            │ 2. 券面マークアップを生成    │
      │                            │ 3. print_jobs に INSERT    │
      │                            │    (status='queued')       │
      │  番号・QR・待ち時間を返す     │                            │
      │◀───────────────────────────┤                            │
      │                            │                            │
      │ 画面に番号を表示（保険）      │                            │
      │                            │◀────POST /cloudprnt────────┤ 10秒ごとの
      │                            │      {status, printerMAC}  │ ポーリング
      │                            │                            │
      │                            ├───{jobReady:true, ...}────▶│
      │                            │                            │
      │                            │◀────GET /cloudprnt?uid=────┤
      │                            ├───券面マークアップ本文──────▶│
      │                            │                            │ ★印刷される
      │                            │◀───DELETE /cloudprnt?uid───┤
      │                            │  status='confirmed' に更新  │
```

**重要な設計判断：印刷は発券処理の成否に影響させない。**
`print_jobs` へのINSERTが失敗しても `issue_ticket` は成功を返す。ゲストは画面の番号とQRで用が足りるため、印刷失敗で発券が止まる事態を避ける。

## 8. 認証・認可の設計

### 8.1 3種類のアクセス経路

| 経路 | 使うキー | できること |
|---|---|---|
| 匿名（キオスク・ゲスト・サイネージ） | `anon` キー | 公開RPC の実行、`queues` / `queue_states` / `tenants` の SELECT のみ |
| スタッフ | `anon` キー + ログイン後のJWT | 自テナントの `tickets` 等の読み書き |
| プリンタ | デバイストークン（URLクエリ） | `cloudprnt` Edge Function のみ |

### 8.2 匿名に許可するRPC

以下の4つのみ `GRANT EXECUTE TO anon` する。それ以外はすべて `authenticated` 限定。

| RPC | 用途 |
|---|---|
| `issue_ticket` | 発券 |
| `get_ticket_status` | QRトークンから自分の状況を取得 |
| `get_public_queues` | キオスク用のキュー一覧取得 |
| `register_push_subscription` | Web Push購読の登録 |

### 8.3 テナント分離

すべてのテーブルに `tenant_id` を持たせ、スタッフのRLSポリシーは以下で統一する。

```sql
USING (tenant_id = (SELECT tenant_id FROM staff WHERE id = auth.uid()))
```

将来グループホテル展開する際も、DDL変更なしで対応できる。

## 9. 障害時の縮退運転

| 障害 | 検知方法 | システムの挙動 | 運用手順 |
|---|---|---|---|
| インターネット断 | `navigator.onLine` + RPCの疎通確認（30秒ごと） | キオスク：全面に「ただいま発券できません。スタッフにお声がけください」<br>スタッフ画面：上部に赤帯警告 | 10分以上続く場合、手書き整理券に切替。復旧後、スタッフが代理発券で番号を引き継ぐ |
| プリンタ用紙切れ | ポーリングの `statusCode` に紙なしビット | スタッフ画面に「用紙切れ」バナー<br>キオスクは通常どおり発券し、画面に番号を大きく表示 | ロール紙を交換。交換後、失敗したジョブを一括再印刷 |
| プリンタ電源断/LAN断 | 60秒以上ポーリングが来ない | スタッフ画面に「プリンタ応答なし」<br>キオスク画面下部に「番号をお控えください」 | 電源・LANケーブルを確認 |
| Supabase障害 | RPCが5xxを返す | インターネット断と同じ扱い | Supabaseのステータスページを確認。手書き運用へ |
| サイネージのクラッシュ | 30秒ごとの自己ヘルスチェック | 自動リロード | 3回連続失敗したら手動でSafariを再起動 |
| キオスクiPadのスリープ | — | — | 設定 > 画面表示と明るさ > 自動ロック を「なし」に。常時給電にする |

## 10. データ保持とプライバシー

| データ | 保持期間 | 削除方法 |
|---|---|---|
| `tickets.room_number` | 90日 | 日次メンテナンスジョブで `NULL` に更新 |
| `tickets`（行そのもの） | 400日 | 日次メンテナンスジョブで削除（統計は `daily_stats` に集約済み） |
| `print_jobs` | 7日 | 日次メンテナンスジョブで削除 |
| `daily_stats` | 無期限 | 集計値のみで個人情報を含まない |
| `push_subscriptions` | チケット終了後24時間 | 日次メンテナンスジョブで削除 |
| `ticket_events`（監査ログ） | 400日 | 日次メンテナンスジョブで削除 |

氏名・電話番号・メールアドレスは**一切収集しない**。これによりプライバシーポリシーの負担と情報漏洩リスクを最小化する。

## 11. バックアップ

Supabase無料プランには自動バックアップがないため、GitHub Actions で代替する。

`.github/workflows/backup.yml`:

```yaml
name: Daily DB Backup
on:
  schedule:
    - cron: '0 18 * * *'   # UTC18:00 = JST 03:00
  workflow_dispatch:

jobs:
  backup:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install PostgreSQL client
        run: |
          sudo apt-get update
          sudo apt-get install -y postgresql-client-16
      - name: Dump database
        env:
          PGPASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}
        run: |
          mkdir -p backups
          pg_dump \
            -h ${{ secrets.SUPABASE_DB_HOST }} \
            -p 5432 -U postgres -d postgres \
            --no-owner --no-privileges \
            -f backups/dump-$(date -u +%Y%m%d).sql
          gzip backups/dump-$(date -u +%Y%m%d).sql
      - name: Prune backups older than 30 days
        run: find backups -name '*.sql.gz' -mtime +30 -delete
      - name: Commit
        run: |
          git config user.name  "backup-bot"
          git config user.email "backup@example.com"
          git add backups
          git diff --staged --quiet || git commit -m "backup $(date -u +%Y-%m-%d)"
          git push
```

> このワークフローは、Supabase無料プロジェクトが「7日間無アクセスで停止」する条件を回避する役割も兼ねる。

## 12. 監視

無料でできる範囲の監視を設定する。

| 対象 | 方法 |
|---|---|
| サイト死活 | UptimeRobot 無料プラン（5分間隔・50モニターまで）でトップページとRPCエンドポイントを監視 |
| プリンタ死活 | `printers.last_seen_at` が3分以上前ならスタッフ画面に警告表示（アプリ内で完結） |
| Edge Function 使用量 | Supabaseダッシュボードで週1回確認。80%を超えたらポーリング間隔を15秒に延ばす |
| エラーログ | Supabase の Edge Function ログを週1回確認 |
